> 新岗位候选判定 + 结构化岗位定义生成 + 人工审核工作流
> 对标题目要求：识别新兴岗位并生成岗位名称、核心职责、必备技能、加分技能、典型行业应用场景，支持人工优化与动态更新

## 链路一四重控制

链路一与链路二共用四重控制框架，具体方法适配新岗位场景：

| 控制 | 方法 | 说明 |
|------|------|------|
| **通胀** | 同公司+文本>80%相似→直接删除克隆JD（从源头消除，非加权降权） | 删除656条克隆（通胀率33.8%），簇大小真实可信 |
| **幻觉** | 自适应3-gram命中率校验 + 告警比阈值回退 | Prompt铁律源头约束，3-gram事后验证 |
| **时滞** | arXiv/GitHub名词→JD首次出现时间差 + 前置召回漏判岗位 | 中位数11个月，标注`time_lag_days` |
| **噪声** | _is_requirement_sentence() 5种需求句模式 + 7类inline噪声正则过滤 | 纯规则初稿零生成噪声 |

### 步骤①：规则判定（new_job_candidate.py）

### 步骤②：arXiv/GitHub 前沿名词召回（前置补充）

**动机**：规则判定依赖JD内AI术语密度，可能漏判以下情况：
- 前沿技术术语在JD中出现但频率不足以触发规则阈值
- 新兴交叉领域（如AI+生物、AI+材料）的岗位，AI术语密度不如纯AI岗位高
- arXiv/GitHub上已有大量讨论但JD市场尚未形成规模的新方向

**流程**：

```
arXiv API (cs.AI/cs.CL/cs.LG) + GitHub trending
    │
    ├─ 采集24个新兴术语（如 MCP, MoE, World Models, 
    │   Diffusion Transformers, Self-evolving, AI Scientist...）
    │
    ├─ 扫描全量25,010条JD → 匹配到新兴术语的JD
    │
    ├─ 排除已被规则判定为新岗位的JD（去重）
    │
    ├─ RAG双锚定验证：
    │   锚1: 3-gram溯源 — 该术语在JD原文中的上下文是否构成独立职责
    │   锚2: arXiv/GitHub交叉验证 — 该术语在学术/开源界的使用是否与JD一致
    │
    └─ 通过验证 → 合并入候选池 → 进入步骤③聚合定义
```

**时滞控制**：arXiv/GitHub信号领先JD需求中位数11个月。新召回岗位标注 `time_lag_days` 字段，供后续动态更新参考。

## 通胀消除（克隆JD删除）

新岗位JD的技能通胀率（70.5%）是全量JD（8.8%）的8倍——公司追热门词大量互相抄，导致技能频率虚高。

`new_job_definition.py` 内置通胀消除：`remove_clone_jds()` 同公司+文本相似度>0.8检测克隆JD并直接删除，仅保留第一条。簇大小和技能支持率均为真实独立JD数。

### 算法

```
输入: 同一岗位簇的N条JD

对于每条JD_i (未被删除):
  对于每条JD_j (j > i, 未被删除):
    IF company_i == company_j AND SequenceMatcher(text_i, text_j) > 0.8:
      标记j为克隆 → 直接删除（仅保留i，即原文最完整的第一条）

输出: [去重后JD列表, clones_removed]
```

### 克隆去重（v12起从源头删除）

| 检测条件 | 处理 |
|---------|------|
| 同公司 + JD文本相似度>0.8 | 直接删除克隆JD，仅保留第一条 |

**效果**：删除656条克隆JD（通胀率33.8%），JD总数1,939→1,283。AI算法工程师簇从274条→59条独立JD。

不再使用权重/降权方式；簇大小和技能支持率均反映真实独立JD数。

## 技能分离阈值

同一簇内所有JD的技能按支持率（去克隆后）分三档：

| 档位 | 支持率 | 去向 | 上限 |
|------|-----------|------|------|
| **必备技能** | ≥15% | `required_skills[]` | 8个 |
| **加分技能（降级）** | 8%~15% | 从必备降级→`bonus_skills[]` | 共用加分池 |
| **加分技能（原始）** | ≥8% | 原始加分列→`bonus_skills[]` | 加分池总计8个 |
| **丢弃** | <8% | 不进入定义 | — |

**设计要点**：
- 15%必备阈值：确保有足够真实支持度
- 必备降级机制：不够15%但≥8%的技能自动降级为加分
- 兜底停止：必备满8个且加分满6个后break

## 核心职责提取管线

两级管线从JD原文提取/合成核心职责：`parse_duties()` → `_synthesize_duties_from_skills()`

**注意**：代码中不存在 `score_duties()` 函数。`parse_duties()` 直接返回过滤后的句子列表，不做打分排序。

### 第一级：parse_duties() — 职责段提取+inline清洗

```
JD原文
  ├─ 段落匹配: "岗位职责"/"工作内容"/"职位描述" 段 → 截取到下一个标题前
  ├─ 兜底: 无明确标题→取全文前50%
  ├─ 拆句: 按 。；\n 拆分（不对，；；如拆分）
  ├─ inline清洗（无独立 _clean_duty_sentence 函数）:
  │   ├─ 去【】[] 标签
  │   ├─ 去列表标记: - • · ▲ ◆ ■ ▼ ► ▪ ① ② ③ 1. 等
  │   ├─ 去段落标题: "岗位职责：" "职责描述：" "工作内容：" 等
  │   └─ 过滤7类噪声: 薪资/福利/公司介绍/招聘套话/联系方式/纯标题行/纯空白
  ├─ _is_requirement_sentence() 过滤5种需求句模式:
  │   ①技能熟练度 ②学历/年限 ③经验/优先 ④工具链首词 ⑤软技能短句
  ├─ 过滤: 长度∉(8,200)丢弃
  └─ 合并: 相邻短句(<15字)合并到前一句
```

### 第二级：_synthesize_duties_from_skills() — 兜底合成

JD格式极不规范（纯技能列表、无职责段）时，从必备技能反推：
- 有技能 → `"负责{岗位名}相关的{skill1}、{skill2}等技术研发与系统开发工作"`
- 空技能 → `"负责{岗位名}相关技术工作，参与系统架构设计与核心模块开发"`

---

## 别称与主名选择

- **主名（canonical）**：直接使用归一化名（`norm_name`），而非原始名投票——避免把"AI开发工程师"叫成"AI工程师"
- **别称（aliases）**：`Counter(原始job_name).most_common(15)` → `dict.fromkeys()` 去重保留顺序 → 排除与主名仅大小写不同的项

## 岗位名归一化规则（5轮顺序正则管线）

纯确定性规则引擎，无拆段、无打分、无"选最佳段"逻辑。

### 流程概览

```
原始岗位名
  ├─ 第1轮 粗清理：去【】[]→去括号(嵌套3轮)→去职级前缀→lower→去空白→去尾部JD编号→去残留单ASCII字母
  ├─ 第2轮 后缀噪音：去尾部编号→去"---公司---城市"→去/实习/全职/应届/社招/校招
  ├─ 第3轮 ★语义归一化：实习生→工程师(复合技术词优先)→RECRUIT_JARGON→C-level过滤→公司前缀→命名规范化→冗余后缀清理→|预分割→残缺后缀修复→研发/应用/开发统一
  ├─ 第4轮 前缀噪音：去公司/部门/项目名前缀(仅ASCII+数字)→去行首残留破折号
  └─ 第5轮 中英混合名：取中文段→"/"".""&"分隔取含角色后缀最长段
       ↓
  最终清理：全局去"实习"→第三遍残缺后缀修复→岗→工程师→裸技术词补工程师→纯英文补工程师→去尾部"岗位"→第二遍非岗位词过滤
```

## CLI 参考

### 基本用法

```bash
# 纯规则模式（默认，零外部依赖）
python new_job_definition.py \
    --input_dir "../08_最终数据/jd_v2/" \
    --output new_job_definitions.json \
    --audit_excel audit_definitions.xlsx

# LLM精炼模式（需 DEEPSEEK_API_KEY 环境变量或LLM_CONFIG中api_key）
python new_job_definition.py \
    --input_dir "../08_最终数据/jd_v2/" \
    --output new_job_definitions.json \
    --audit_excel audit_definitions.xlsx \
    --use_llm
```

### 参数一览

| 参数 | 类型 | 默认值 | 说明 |
|------|------|--------|------|
| `--input_dir` | str | **必填** | 已标注CSV目录 |
| `--output` | str | `new_job_definitions.json` | 输出JSON路径 |
| `--audit_excel` | str | 空（不导出） | 审核Excel路径，如 `audit_definitions.xlsx` |
| `--timeline_report` | str | 空 | 能力动态更新报告，关联趋势数据 |
| `--use_llm` | flag | False | 启用LLM精炼（需 `DEEPSEEK_API_KEY` 或 `LLM_CONFIG.api_key`） |
| `--llm_max` | int | 999 | LLM精炼最多处理前N个岗位（默认全量） |

### 纯规则 vs LLM精炼

| 维度 | 纯规则 (默认) | LLM精炼 (--use_llm) |
|------|--------------|---------------------|
| 依赖 | Python stdlib + pandas | + DeepSeek API |
| 确定性 | 100%可复现 | 受temperature影响 |
| 核心职责 | 从JD原文截取+排序 | LLM凝练≤30字/条 |
| 行业场景 | 公司名正则匹配 | LLM从JD描述推断 |

### 策略演进（三轮迭代）

| 阶段 | 日期 | 闸门 | 覆盖 | 结果 |
|------|------|------|------|------|

**关键决策**：`_FRONTIER_AI_RE` 保留在代码中但不再用于闸门判断，可供后续按需启用。

### 流程

```
规则初稿 → build_llm_prompt()（6条铁律源头约束）→ DeepSeek API → 解析JSON
    → verify_llm_duties() → 自适应3-gram命中率检查 + 告警比检查
        → 两项均通过: 采纳LLM输出
        → 任一失败: 回退规则版
```

### Prompt内容

发送给LLM的数据全部来自源统计，不掺杂模型知识。6条铁律约束LLM行为：
1. 职责≠要求（附正反例）
2. 每条以动词开头
3. 8~30字/条
4. 5~8条，按重要性降序
5. 语义重复合并
6. 从候选筛选，不编造

### 幻觉校验（仅自适应3-gram，2项检查）

| 检查项 | 方法 | 阈值 |
|--------|------|------|
| 自适应3-gram | LLM输出每条职责句3-gram vs 源JD原文命中率 | 簇≥15条:≥15%; 簇≥8:≥12%; 簇≥4:≥8%; 簇<4:≥5% |
| 自适应告警比 | 不达标职责数/总职责数 | 簇≥10:≤50%; 簇≥5:≤60%; 簇<5:≤75% |

**注意**：代码中不存在 FORBIDDEN_PATTERNS/句数/去重/残留标签等额外检查层。3-gram+告警比是仅有的两个验证逻辑。

### 容错

- API Key未设置 → 自动退纯规则，打印提示
- API调用失败（**5次重试**，遇connection error/timeout/rate limit递增等待） → 该条定义保留规则版
- JSON解析失败 → 尝试正则提取，仍失败则回退
- 幻觉校验不通过 → 打印告警数，回退规则版
- **UnicodeEncodeError**（Windows GBK终端生僻字） → try-except fallback打印 `(name#{id})`

**`infer_industry()` 核心逻辑（加权打分取最高分）**

```python
# new_job_definition.py 行694-719
def infer_industry(company_name, work_area='', jd_text='', job_name=''):
    scores = {}
    for pattern, industry in INDUSTRY_MAP:
        nm_matches = len(re.findall(pattern, name_text))   # 岗位名命中
        jd_matches = len(re.findall(pattern, jd_full))     # JD文本命中
        co_matches = len(re.findall(pattern, company_text)) # 公司名命中
        if nm_matches > 0 or jd_matches > 0 or co_matches > 0:
            scores[industry] = nm_matches * 5 + jd_matches * 2 + co_matches
            #                   岗位名权重×5 > JD文本×2 > 公司名×1
    if scores:
        return max(scores, key=scores.get)  # 取最高分，非首命中
    return '通用信息技术'
```

权重设计：岗位名×5（最准）> JD职责文本×2 > 公司名/工作地点×1。JD关键词兜底（`INDUSTRY_JD_KEYWORDS`）仅在打分阶段无匹配时触发。

### 修复8: 通胀输出 (2026-08-10)

**问题**：`source_traceability` 需同时展示原始JD数和通胀矫正后的有效JD数，供审核时判断数据质量。

**当前实现**（`build_definition()` 行1430-1438）：

```python
'source_traceability': {
    'total_jds': n,                               # 簇内原始JD总数
    'effective_jds': round(total_weight, 1),      # Jaccard去重后有效JD数
    'unique_companies': len(company_set),
    'top_companies': company_set[:5],
    'top_cities': city_set[:5],
    'inflation_ratio': round(inflation_ratio, 2),       # 通胀比例(0~1)
    'inflation_severity': inflation_severity,            # 加权严重度: 重度×1.0+中度×0.5
    'inflation_breakdown': {                             # 通胀分级统计
        '重度(簇≥3)': inflate_heavy,
        '中度(簇=2)': inflate_medium,
        '无': inflate_clean,
    },
},
```

- `effective_jds`：Jaccard抄袭簇降权后的有效JD计数（同 `graph_calibrator.py` 的 `InflationCalibrator`）
- `inflation_ratio`：通胀比例，0=无通胀（所有JD独立），1=全部严重通胀
- `inflation_breakdown`：按簇大小分级统计，≥3条同文本=重度，2条=中度
- 技能支持率统一展示 `support_pct`(原始) → `support_pct_corrected`(矫正后)
